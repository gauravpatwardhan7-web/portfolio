Rebuilding a Petrel plugin with AI agents

Gaurav Patwardhan · Shell, Subsurface & Wells

Shell's subsurface teams run about 22 in-house plugins inside Petrel, the software our geologists and engineers work in every day. Those plugins are built on a vendor SDK, and that SDK ships a deprecation release every year. When it does, someone has to go through each plugin and fix everything the new version broke before the teams can use it again. That was taking roughly six weeks of engineering time per plugin.

I took one plugin and rebuilt it with AI agents instead.

The obvious approach is to paste the code into a chat window and ask for a fix, and it doesn't work. The model writes something that looks right, and in a geoscience tool a patch that looks right but isn't is worse than no patch at all — finding the mistake three months later costs more than doing the work by hand would have. The hard part was never generating the change. It was knowing whether to trust it.

So I set it up as two agents, with four things built around them:

  • Tools — so the agents could read the codebase and the SDK directly, instead of me pasting snippets back and forth and hoping I'd pasted the right ones.
  • Skills — the migration knowledge our senior engineers carry in their heads, written down once so the agents load it on every run rather than rediscovering it each time.
  • A test playbook — what to run, in what order, to prove the migration actually held.
  • Acceptance criteria — a written definition of done, so the output is checked against a standard instead of against whoever happens to be reviewing that day.

Most of the work went into the last two. The first two are setup; the last two are the reason anyone can rely on what comes out.

The plugin came through in about a week instead of six.

Two things worth saying about that. The reusable part isn't the patched plugin — it's the harness and the written-down migration knowledge, and both of those still hold for next year's SDK release. And AI made the recurring work cheaper without making it stop recurring, so alongside this I scoped an adapter pattern that isolates the SDK calls, so a deprecation release changes one layer instead of the whole plugin.

On the back of the one plugin, a five-plugin pilot was approved.
